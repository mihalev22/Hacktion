# Кейс-3: «Из разговора — в ТЗ» | Автоматическое формирование требований

X\<актион> ТехЗадание — AI-сервис, который превращает запись встречи заказчика и технического специалиста в проверяемое техническое задание: с цитатами, таймкодами, ролями, приоритетами и открытыми вопросами.

_Внутреннее рабочее название проекта — RequireX (отсюда имя файла базы данных `requirex.db` и заголовок API в коде); в интерфейсе и документации используется актуальное имя выше._

## Развёрнутый проект

Проект развёрнут на арендованном сервере в Selectel и доступен для оценки по адресу:

**http://91.206.14.15:8080/**

После делегирования будет выпущен SSL-сертификат, и проект перейдёт на защищённое соединение по HTTPS.

## Описание решения

- **Проблема:** после встречи с заказчиком технический специалист вручную пересматривает запись, конспектирует требования, ограничения и договорённости — это занимает часы, а часть деталей (скрытые условия, оговорки, смена решения по ходу разговора) неизбежно теряется.
- **Наше решение:** веб-приложение, в которое загружается аудио- или видеозапись встречи. Сервис автоматически расшифровывает разговор с разделением по спикерам, с помощью LLM (GigaChat) извлекает функциональные и нефункциональные требования, роли, ограничения, открытые вопросы и user stories, а затем даёт пользователю проверить, отредактировать и экспортировать результат — с возможностью в один клик перейти к фрагменту записи, из которого взято требование.
- **Целевая аудитория:** системные и бизнес-аналитики, тимлиды, project-менеджеры, разработчики, которым нужно быстро получить формализованное ТЗ по итогам переговоров.

## Основной пользовательский сценарий (User Journey)

1. **Регистрация / вход** — пользователь создаёт аккаунт или заходит под демо-доступом (`demo@akcion.tech`), либо открывает готовый демо-пример без авторизации.
2. **Загрузка медиа** — пользователь создаёт встречу и загружает аудио- или видеофайл (`POST /api/meetings`); файл сохраняется, если видео — из него будет извлечена аудиодорожка.
3. **Обработка и анализ ИИ** — фоновая задача (`BackgroundTasks`) проходит пайплайн: `extracting → transcribing → analyzing → done`, статус встречи виден в интерфейсе в реальном времени.
   - Извлечение звука из видео через FFmpeg (если нужно);
   - Расшифровка с диаризацией спикеров через speech2text.ru;
   - Извлечение требований через GigaChat по структурированному промпту с обязательной цитатой-источником;
   - Отдельный проход поиска противоречий между требованиями и внутри разговора (ретракты — «сначала согласился, потом передумал»);
   - Валидация: степень совпадения цитаты LLM с реальным текстом транскрипта пересчитывается на бэкенде (`rapidfuzz`) и становится `confidence`, а не берётся на веру у модели.
4. **Генерация категорий ТЗ** — результат раскладывается по разделам: функциональные требования, нефункциональные требования, ограничения, роли, открытые вопросы, противоречия, user stories.
5. **Проверка и редактирование в интерфейсе** — пользователь просматривает ТЗ, редактирует и удаляет требования, добавляет свои вручную, помечает пункты как «требует уточнения», закрывает открытые вопросы, разрешает противоречия.
6. **Переход по таймлайну** — клик по требованию прокручивает и подсвечивает соответствующий фрагмент транскрипта и аудио, чтобы быстро проверить корректность результата.
7. **Экспорт** — готовое ТЗ выгружается в Markdown (`GET /api/meetings/{id}/export`) или скачивается как PDF прямо из интерфейса.

## Архитектура приложения

Приложение построено как классическое SPA с REST API и фоновой асинхронной обработкой файлов через внешние AI-сервисы. Frontend — React 19 + TypeScript, собранный Vite и раздаваемый nginx, который одновременно проксирует запросы `/api` на backend внутри одной Docker-сети: это снимает вопросы с CORS и позволяет использовать HttpOnly-cookie без дополнительных настроек. Backend — FastAPI-приложение с роутерами `auth`, `projects`, `meetings` и `admin`; аутентификация построена на JWT (короткий access-токен и более долгий refresh, оба в HttpOnly-cookie), пароли хранятся в виде scrypt-хешей. Данные — пользователи, проекты, встречи, сегменты транскрипта, требования, открытые вопросы, противоречия и user stories — живут в SQLite через SQLAlchemy ORM.

Ключевая часть системы — фоновый пайплайн обработки встречи (`services/pipeline.py`), запускаемый через `BackgroundTasks` сразу после загрузки файла, чтобы не блокировать ответ пользователю. Если загружено видео, FFmpeg сначала проверяет наличие аудиодорожки и извлекает звук в моно WAV 16 кГц; дальше и аудио, и извлечённая из видео дорожка идут по одному и тому же пути. Файл отправляется во внешний сервис speech2text.ru, который делает расшифровку с разделением по спикерам и таймкодами. Полученный транскрипт передаётся в GigaChat вместе со строгим системным промптом (`docs/gigachat_prompt.md`), который требует вернуть единственный JSON с требованиями, ограничениями, открытыми вопросами и user stories, причём каждый пункт обязан ссылаться на дословную цитату из разговора. Отдельным, вторым вызовом та же модель анализирует получившийся список требований вместе с полной транскрипцией и ищет противоречия — как логические конфликты между пунктами, так и случаи, когда говорящий менял решение по ходу встречи.

Ответу модели бэкенд не доверяет вслепую: для каждой цитаты, которую LLM указала как источник, `rapidfuzz` ищет наиболее похожий сегмент в реальном транскрипте и пересчитывает степень совпадения — именно это значение, а не самооценка модели, становится `confidence` требования и определяет, ставить ли флаг «требует уточнения». Статус встречи на всех этапах фиксируется в БД, поэтому если backend-процесс перезапустится посреди обработки, при старте приложения такие «зависшие» встречи автоматически переводятся в статус ошибки с понятным пользователю текстом, а исходный файл остаётся на диске — обработку можно запустить заново без повторной загрузки.

## Реализованный функционал

### Базовые требования кейса (обязательный MVP)

- Загрузка аудио/видео записей популярных форматов — аудио: `mp3, wav, m4a, aac, ogg, flac`; видео: `mp4, mov, avi, mkv, webm` (аудиодорожка извлекается через FFmpeg с проверкой magic bytes, а не только по расширению).
- Автоматический анализ и выделение ключевых категорий — функциональные и нефункциональные требования, роли пользователей, ограничения (`constraints`), открытые вопросы (`open_questions`), договорённости (в саммари встречи) и user stories.
- Табличное / структурированное представление ТЗ — требования сгруппированы по типу, приоритету и ролям в отдельном экране «Спецификация» для каждой встречи.
- Интерактивное редактирование — полноценный CRUD требований (создание вручную, правка, удаление), отметка «требует уточнения», разрешение и переоткрытие открытых вопросов, разрешение противоречий.
- Привязка требований к таймлайну разговора (sourcing и verification) — каждое требование хранит точную цитату и тайм-код исходного сегмента (`source_segment_id`, `source_start_sec/end_sec`); клик по требованию скроллит и подсвечивает нужное место в транскрипте и аудиоплеере.

## Использование ИИ в разработке (AI Usage Manifest)

В соответствии с правилами хакатона команда использовала ИИ-инструменты на следующих этапах:

- **Проектирование архитектуры и модели данных** — обсуждение и уточнение схемы сущностей (встречи, требования, сегменты транскрипта, противоречия, user stories) с ИИ-ассистентом.
- **Генерация и итеративная доработка системного промпта для GigaChat** — промпт в `docs/gigachat_prompt.md` формировался и отлаживался итеративно с помощью ИИ, чтобы добиться строгого JSON-формата, привязки требований к дословным цитатам и корректной классификации приоритетов.
- **Написание и рефакторинг кода** — как backend (FastAPI-роутеры, сервисы обработки, миграции SQLite «на лету»), так и frontend (React-компоненты, хуки, работа с API).
- **Работа с кодовой базой через API** — часть кода писалась и рефакторилась ИИ-агентом, работающим напрямую с файлами репозитория через API модели (Claude API / Claude Code), а не только через диалоговый интерфейс — это позволяло вносить правки сразу в несколько файлов проекта и запускать команды (сборку, линтинг, тесты) в рамках одной задачи.
- **Работа с текстом и документацией** — подготовка README, комментариев в коде, пользовательских текстов ошибок на русском языке.
- **Интеграция LLM** — проектирование связки speech2text.ru → GigaChat → валидация цитат внутри AI-пайплайна.

Инструменты: ассистенты на базе больших языковых моделей (Claude и аналогичные ИИ-помощники для разработки).

## Ограничения MVP

Честно о текущих ограничениях решения:

- **Зависимость от внешних API** — распознавание речи (speech2text.ru) и AI-анализ (GigaChat) требуют действующих ключей и доступа в интернет; при их отсутствии или сбое обработка встречи завершается ошибкой с понятным текстом (файл при этом сохраняется, и обработку можно повторить без повторной загрузки).
- **Скорость обработки** — время формирования ТЗ линейно зависит от длительности записи и от очереди/скорости ответа внешних сервисов (распознавание + два последовательных вызова LLM); для длинных встреч (более часа) обработка может занимать несколько минут.
- **Качество распознавания и разделения спикеров** — целиком определяется внешним STT-сервисом; на зашумлённых записях или при перекрывающейся речи возможны ошибки диаризации, которые могут повлиять на итоговую атрибуцию требований.
- **TLS-соединение с GigaChat** — сертификат Сбера идёт в self-signed цепочке; по умолчанию для демо используется `verify=False` (осознанный компромисс хакатона), для продакшена предусмотрена корректная проверка через `GIGACHAT_CA_BUNDLE`.
- **Пайплайн живёт в памяти процесса** — фоновая обработка не переживает перезапуск backend-контейнера: «зависшие» встречи после рестарта автоматически помечаются ошибкой (без потери загруженного файла), но потребуют повторного запуска обработки.
- **Ограничение размера файла** — по умолчанию 200 МБ на загрузку (настраивается через `MAX_UPLOAD_MB`), согласовано между фронтендом и конфигурацией nginx.
- **Хранилище — SQLite** — оптимально для MVP и демо-сценария хакатона; для продакшен-нагрузки с высокой конкурентностью потребуется миграция на клиент-серверную СУБД (PostgreSQL и подобные).
- **Полнотекстовый поиск по транскрипту** — на данный момент поиск реализован по названию встречи, а не по содержимому расшифровки.

## Инструкция по запуску

### Быстрый запуск через Docker Compose

```bash
cp .env.example .env
```

Заполните `.env` в корне проекта:

```dotenv
# переменные для docker compose (файл положить рядом как .env)
S2T_API_KEY=                     # ключ API speech2text.ru
GIGACHAT_CLIENT_ID=              # SberWave client id для OAuth GigaChat
GIGACHAT_CLIENT_SECRET=          # SberWave client secret
JWT_SECRET=change-me-in-production   # сгенерировать: python -c "import secrets;print(secrets.token_urlsafe(48))"
ADMIN_EMAIL=                     # email, который станет админом системы
SHOW_DEMO_HINT=true              # false на публичном сервере — скрыть демо-логин
COOKIE_SECURE=false              # true только при HTTPS
```

Запуск:

```bash
docker compose up --build
```

Приложение будет доступно на `http://localhost:8080` (frontend на nginx проксирует `/api` на backend в одной Docker-сети — CORS и cookies работают без дополнительной настройки). БД и загруженные файлы сохраняются в именованных volumes (`dbdata`, `uploads`).

## Переменные окружения (`backend/.env`)

| Переменная                                                  | Назначение                                                                                    |
| ----------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| `S2T_API_KEY`                                               | ключ API speech2text.ru (расшифровка аудио)                                                   |
| `GIGACHAT_CLIENT_ID` / `GIGACHAT_CLIENT_SECRET`             | креды SberWave OAuth для GigaChat                                                             |
| `GIGACHAT_CA_BUNDLE` / `GIGACHAT_VERIFY_SSL`                | корректная проверка TLS-сертификата Сбера (или осознанный компромисс `verify=false` для демо) |
| `DATABASE_URL`                                              | по умолчанию — абсолютный путь `backend/requirex.db`                                          |
| `MAX_UPLOAD_MB`                                             | лимит размера загружаемого файла (по умолчанию 200 МБ)                                        |
| `JWT_SECRET`                                                | секрет подписи токенов (обязателен в проде; иначе генерируется временный)                     |
| `ACCESS_TOKEN_EXPIRE_MINUTES` / `REFRESH_TOKEN_EXPIRE_DAYS` | сроки жизни access/refresh токенов (15 мин / 7 дней)                                          |
| `ADMIN_EMAIL`                                               | email, которому автоматически выдаётся системная роль `admin`                                 |
| `SHOW_DEMO_HINT`                                            | показывать ли демо-логин на экране входа                                                      |
| `COOKIE_SECURE`                                             | `true` только при развёртывании через HTTPS                                                   |

Реальные значения `.env` не коммитятся и не должны попадать в архив на демонстрацию — `.gitignore` уже настроен.

## Проверки и тесты

- `python scripts/eval_tests.py` — eval AI-конвейера без сети: парсер speech2text (нativenый формат, альтернативные ключи, мусор-входы, слияние сегментов), golden-контракт mock-ответа со схемой промпта, «стресс» ingestion (`store_analysis`) на выдуманных/битых полях модели (несуществующие тип/priority, дубли REQ-id, строки вместо массивов ролей), фактическая проверка цитат (`_validate_quotes` downgrade confidence), криптография (scrypt + JWT typ), magic-bytes фильтр загрузок. 12 тестов.
- `python scripts/smoke_check.py` — интеграция API: auth-границы, CRUD, загрузки (формат/магия/пустой), rate-limit.
- `python scripts/qa_idor_check.py` — безопасность: 36 проверок доступа между двумя пользователями (IDOR GET/POST/PATCH/DELETE, viewer-read-only, anon-401).
- Браузерный E2E (Playwright) перед демо: весь путь от логина до PDF, persistence после F5, responsive 375–1920, консоль/сеть без ошибок.

## Известные ограничения (осознанный MVP-трейд-офф)

- Фоновый пайплайн живёт в процессах FastAPI; при рестарте контейнера прерванные встречи возобновляются автоматически (`_recover_stuck_meetings/_resume_stuck`). Для горизонтального масштабирования — вынос в Celery/RQ + Redis.
- SQLite (WAL + busy_timeout) достаточен для нагрузки хакатона; для многопоточной записи в проде — PostgreSQL (достаточно сменить `DATABASE_URL`, ORM-слой не меняется).
